## **1. Вступ**

### **Що ми будемо робити?**

Наше завдання — створити сервіс для перегляду та зберігання зображень у вигляді веб-додатку.
Суть проста: користувач заходить на сайт, завантажує фотки чи картинки,
а натомість отримує прямі посилання на них.
Ці посилання можна використовувати де завгодно — у соцмережах, блогах або просто надіслати друзям.

### **Які технології використовуємо?**

- Бекенд пишемо на Python — він чудово підходить для таких завдань.
- Для швидкої роздачі зображень використовуємо Nginx — він просто створений для цього.
- Все запакуємо в Docker-контейнери, щоб проект легко запускався на будь-якому комп'ютері.
- Docker Compose допоможе керувати всіма компонентами як єдиним цілим.

### **Навіщо цей проект?**

Наш сервіс — це не просто сховище зображень. Це місце, де користувачі можуть:
- Завантажувати фотки в популярних форматах (.jpg, .png, .gif).
- Бути впевненими, що їхні зображення надійно збережені.
- Отримувати зручні прямі посилання на завантажені зображення.

Ну а ми, розробники, будемо стежити за всім процесом через систему логів,
щоб знати, що робити, якщо щось піде не так.

А для навчання цей проект — чудовий шанс покращити свої навички в Python-розробці, налаштуванні веб-серверів,
роботі з Docker та взаємодії різних компонентів системи один з одним.

### **Основні завдання:**

## **2. Функціональні вимоги**

### Основний функціонал:

**1. Головна сторінка**

- **Маршрут:** `/`
- Функціональність:
  - Зустрічає користувача вітальним повідомленням та розповідає про сервіс.
  - Містить посилання на основні маршрути:
  - Сторінка завантаження зображень (`/upload`).
  - Каталог завантажених зображень (`/images/`).

**2. Завантаження зображень**

- **Маршрут:** `/upload`
- **Метод:** `POST`
- Функціональність:
   - Приймає файл зображення від користувача через HTTP-запит.
   - Підтримувані формати: `.jpg`, `.png`, `.gif`.
   - Обмеження розміру файлу: до 5 МБ.
   - Генерує унікальне ім'я для кожного завантажуваного зображення.
   - Зберігає зображення в папку `/images` на сервері.
   - Повертає користувачу унікальний ідентифікатор файлу та посилання на зображення.

**3. Доступ до завантажених зображень**

- **Маршрут:** `/images/<ім'я_файлу>`
- Функціональність:
   - Всі завантажені зображення мають бути доступні для перегляду та завантаження за прямими посиланнями.
   - Nginx обслуговує цей маршрут, роздаючи файли з папки `/images`.

**4. Логування дій**

- Функціональність:
  - Записує кожну дію користувача в лог-файл `app.log`.
- Формат запису:
   ```txt
   [Дата/час] Дія: повідомлення
   ```
Приклади записів:
   ```text
   [2025-01-24 14:00:00] Успіх: зображення img1.jpg завантажено.
   [2025-01-24 14:01:00] Помилка: непідтримуваний формат файлу (user_file.txt).
   ```
- Логи потрібно зберігати в окремому томі Docker.

------

### **Користувацькі сценарії**

**1. Завантаження зображення**
1. Користувач переходить на маршрут `/upload`.
2. Завантажує файл через HTTP-запит (наприклад, за допомогою форми або програми `curl`).
3. Бекенд перевіряє формат та розмір файлу.
4. Якщо файл успішно завантажено:
   - Він зберігається в папці `/images`.
   - Користувачу повертається повідомлення з унікальним посиланням на файл (наприклад, `/images/img1.jpg`).
5. Якщо файл не відповідає вимогам:
   - Користувачу повертається повідомлення про помилку (наприклад, "Непідтримуваний формат файлу").

**2. Перегляд завантажених зображень**
1. Користувач переходить за посиланням `/images/<ім'я_файлу>`.
2. Nginx повертає запитане зображення для перегляду або завантаження.

## **3. Нефункціональні вимоги**

### **1. Продуктивність**

- **Багатозадачність:** сервер легко справляється з 10 користувачами, які завантажують картинки одночасно. Жодних гальмувань та зависань!
- **Швидкість завантаження:** час обробки завантаження одного зображення (включаючи збереження та генерацію імені) не повинен перевищувати 1 секунди.
- **Миттєвий перегляд:** Nginx роздає картинки зі швидкістю світла (ну гаразд, менше 100 мілісекунд).
  Відкрили посилання — відразу побачили картинку, жодного "завантажується...". Коротше кажучи, все має працювати швидко та без затримок! ⚡

### **2. Обмеження**

- **Розмір файлів:** максимальний розмір завантажуваного зображення — 5 МБ.
- **Підтримувані формати:** тільки `.jpg`, `.png` та `.gif`. Спроба завантажити непідтримуваний формат має повертати повідомлення про помилку.
- **Обсяг зберігання:** сховище зображень не повинно перевищувати доступний простір тому Docker (за замовчуванням обмежень на обсяг не вводиться, але передбачається розумне використання дискового простору).

### **3. Надійність**

- Система має коректно обробляти некоректні запити:
- Завантажені файли, що не відповідають формату або розміру, мають викликати повернення помилки (400 Bad Request).
- У разі збою сервер має автоматично перезапускатися (мається на увазі використання Docker для автоматичного відновлення).

### **4. Масштабованість**

## **4. Архітектура та структура**

### **1. Загальна архітектура**

Система складається з двох основних компонентів:
1. **Python-бекенд:**
- Відповідає за обробку HTTP-запитів, завантаження зображень, валідацію даних та логування.
- Виконує бізнес-логіку додатку, пов'язану з керуванням завантаженими файлами.
- Працює всередині Docker-контейнера, слухаючи запити на порту `8000`.
2. **Nginx-сервер:**
- Роздає статичні файли та завантажені зображення за маршрутом `/images/`.
- Проксує запити на Python-бекенд для інших маршрутів.
- Працює в окремому Docker-контейнері, слухаючи запити на порту `80`.

Компоненти взаємодіють через локальну мережу, створену за допомогою Docker Compose.

### **2. Взаємодія компонентів**

**Коли користувач завантажує картинку:**
1. Користувач надсилає файл через `POST /upload` на Python-бекенд.
2. Бекенд бере всю роботу на себе:
    - Перевіряє, чи все гаразд з файлом
    - Придумує йому унікальне ім'я
    - Зберігає в папку `/images` через Docker volume
    - Записує в лог, що і коли завантажили
    - Віддає користувачу посилання на його картинку

**Коли користувач хоче подивитися картинку:**
1. Запитує картинку через `GET /images/<ім'я_файлу>` у Nginx
2. Nginx шукає файл у папці `/images`
3. Якщо знайшов - віддає картинку користувачу

**Хто за що відповідає:**
- Python-бекенд — "розумна" частина: перевіряє файли, обробляє завантаження
- Nginx — "швидка" частина: роздає картинки і працює як проксі

### **3. Структура проекту**

**Директорії та файли:**
```text
project/
├── app.py                # Основний Python-бекенд
├── requirements.txt      # Залежності Python
├── Dockerfile            # Dockerfile для Python-бекенду
├── docker-compose.yml    # Конфігурація Docker Compose
├── nginx.conf           # Конфігурація Nginx
├── images/              # Папка для зберігання завантажених зображень (volume)
├── logs/                # Папка для логів (volume)
└── static/              # Додаткові статичні файли (CSS/JS, якщо застосовно)
```

**Опис ключових компонентів:**
1. **app.py:**
- Реалізує обробку HTTP-запитів:
    - `GET /` — головна сторінка.
    - `POST /upload` — завантаження зображення.
- Виконує:
    - Валідацію завантажуваного файлу (формат, розмір).
    - Збереження файлу в папку `/images`.
    - Логування дій у файл `app.log`.
  
2. **nginx.conf:**
- Роздає вміст папки `/images` за маршрутом `/images/<ім'я_файлу>`.
- Проксує запити, не пов'язані зі статикою, на Python-бекенд.

3. **compose.yaml:**
- Визначає два сервіси:
    - `app` — Python-бекенд.
    - `nginx` — Nginx-сервер.
- Створює два томи:
    - `images` — для зберігання завантажених зображень.
    - `logs` — для зберігання логів.
  
4. **images/:**
- Каталог, у який зберігаються всі завантажені файли.
- Підключається як volume для довготривалого зберігання.

5. **logs/:**
- Каталог, що містить лог-файли (`app.log`).
- Підключається як volume для збереження даних між перезапусками.

    - Внутрішня мережа Docker зв'язує два контейнери:
    - Nginx звертається до Python-бекенду за адресою `http://app:8000`.

### **5. Логічна схема**

1. **Користувацький запит:**
   Користувач взаємодіє з системою через маршрути:
   - `/` — головна сторінка (обробляється бекендом).
   - `/upload` — завантаження зображення (обробляється бекендом).
   - `/images/<ім'я_файлу>` — доступ до зображення (обробляється Nginx).

2. **Обробка запитів:**
   - Nginx:
       - Роздає статичні файли та завантажені зображення.
       - Переадресовує запити на Python-бекенд, якщо маршрут не пов'язаний з інтерфейсом та зображеннями.
   - Python-бекенд:
       - Приймає і обробляє запити `/` та `/upload`.
       - Зберігає зображення та записує логи.
     
3. **Зберігання даних:**
   - Зображення:
       - зберігаються в volume, підключеному як `/images`.
   - Логи:
       - зберігаються в volume, підключеному як `/logs`.

### **6. Потік даних**

1. **Завантаження зображення:**
   - Користувач надсилає файл на маршрут `/upload`.
   - Python-бекенд:
       - Перевіряє файл.
       - Зберігає файл в `/images`.
       - Логує дію.
   - Користувачу повертається посилання виду `/images/<ім'я_файлу>`.
   
2. **Доступ до зображення:**
   - Користувач надсилає запит на `/images/<ім'я_файлу>`.
   - Nginx перевіряє файл у папці `/images` і повертає його.

# Сервер зображень

Простий веб-сервіс для завантаження та зберігання зображень: користувач завантажує картинку через веб-інтерфейс і отримує пряме посилання на неї. Дані про кожну картинку зберігаються в PostgreSQL, а список усіх картинок можна переглядати посторінково і видаляти непотрібні.

Бекенд - Python (стандартна бібліотека + Pillow + psycopg2), база даних - PostgreSQL, роздача зображень і статики - Nginx, запуск - Docker Compose.

## Можливості

- завантаження `.jpg`, `.png`, `.gif` розміром до 5 МБ;
- перевірка **справжнього** формату файлу через Pillow, а не за розширенням в імені;
- унікальні імена файлів (UUID), тож завантаження не перезаписують одне одного;
- метадані кожної картинки (ім'я, оригінальна назва, розмір, час, формат) зберігаються в таблиці `images` PostgreSQL;
- якщо база недоступна, файл не залишається на диску, а причина пишеться в лог;
- сторінка `/images-list` з таблицею всіх зображень, по 10 на сторінку, найновіші зверху;
- мініатюри в списку: при завантаженні Pillow робить зменшену копію до 120x120, її роздає Nginx;
- видалення зображення кнопкою "Видалити": зникає і запис у базі, і файл на диску разом з мініатюрою;
- прямі посилання виду `/images/<ім'я_файлу>`, які роздає Nginx;
- резервне копіювання бази скриптом `backup.py` у папку `backups/`;
- логування всіх дій у `app.log` у форматі `[Дата/час] Дія: повідомлення`;
- зображення, логи та база живуть у Docker-томах і переживають перезапуск контейнерів.

Параметри бази задаються в одному місці - у файлі `.env` у корені проєкту. `docker compose` читає його сам і передає ті самі значення і сервісу `db`, і бекенду `app`.

| Змінна | За замовчуванням | Що це |
| --- | --- | --- |

| `POSTGRES_USER` | `postgres` | користувач бази |
| `POSTGRES_PASSWORD` | `password` | пароль бази |
| `DB_HOST` | `db` | хост бази для бекенду (ім'я сервісу в `compose.yaml`) |
| `DB_PORT` | `5432` | порт бази для бекенду |

У git лежить тільки приклад `.env.example`. Сам `.env` у git не потрапляє (`.gitignore`), бо в ньому пароль. Якщо `.env` немає, `compose.yaml` підставляє значення за замовчуванням з таблиці, тому проєкт запускається одразу після клонування.

Щоб змінити значення:


і відредагувати `.env`. Назва бази, користувач і пароль застосовуються тільки при першому створенні тому `db_data`, тому після їх зміни потрібно `docker compose down -v`.

## База даних

Сервіс `db` у `compose.yaml`: образ `postgres:17-alpine`, контейнер `postgres_container`, база, користувач і пароль з `.env` (за замовчуванням `images_db`, `postgres`, `password`). Дані лежать у томі `db_data`.

Таблиця `images` (`db/init.sql`):

| Поле | Тип | Що зберігає |
| --- | --- | --- |
| `id` | `SERIAL PRIMARY KEY` | унікальний ідентифікатор запису |
| `filename` | `TEXT NOT NULL` | унікальне ім'я файлу, згенероване сервером |
| `original_name` | `TEXT NOT NULL` | назва файлу, з якою його завантажив користувач |
| `size` | `INTEGER NOT NULL` | розмір файлу в байтах |
| `upload_time` | `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | дата та час завантаження |
| `file_type` | `TEXT NOT NULL` | формат файлу: `jpg`, `png` або `gif` |

Бекенд підключається до бази через psycopg2 з параметрами зі змінних оточення `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `DB_HOST`, `DB_PORT` - тих самих, що й у сервісу `db` (див. Як працює завантаження:

1. Файл перевіряється і записується в `/images` під унікальним ім'ям.
2. Pillow робить мініатюру в `/images/thumbs/` з тим самим ім'ям (див. [Мініатюри](#мініатюри)).
3. У таблицю `images` додається запис (`INSERT ... RETURNING id`).
4. Якщо база не відповіла, щойно записані файл і мініатюра видаляються, клієнт отримує помилку 500, а причина пишеться в `app.log`.

Переглянути дані вручну:

```bash
docker exec -it postgres_container psql -U postgres images_db -c "SELECT * FROM images ORDER BY upload_time DESC;"
```

## Маршрути

| Маршрут | Метод | Що робить | Хто обробляє |
| --- | --- | --- | --- |
| `/` | GET | головна сторінка з описом сервісу та посиланнями | бекенд |
| `/upload` | GET | сторінка-форма завантаження | бекенд |
| `/upload` | POST | приймає файл, перевіряє, зберігає файл і метадані, повертає посилання | бекенд |
| `/images-list` | GET | таблиця зображень з бази, перша сторінка | бекенд |
| `/images-list?page=N` | GET | сторінка N списку | бекенд |
| `/delete/<id>` | POST | видаляє запис з бази і файл з диска, повертає на список | бекенд |
| `/images/<файл>` | GET | віддача самого зображення | Nginx |
| `/images/`, `/gallery` | GET | старі адреси каталогу, перенаправляють на `/images-list` | бекенд |

### POST /upload

Успішна відповідь:

```json
{"id": "3f2a1c....png", "url": "/images/3f2a1c....png"}
```

Помилка 400 - непідтримуваний формат, файл більший за 5 МБ, пошкоджений файл або запит не у форматі `multipart/form-data`:

```json
{"error": "непідтримуваний формат файлу"}
```

Помилка 500 - файл не вдалося записати на диск або зберегти метадані в базу:

```json
{"error": "не вдалося зберегти дані про файл"}
```

### GET /images-list

Таблиця з колонками: прев'ю (мініатюра, клік відкриває оригінал), назва файлу (посилання на `/images/<файл>`), оригінальна назва, розмір у КБ, дата та час завантаження, тип файлу і кнопка "Видалити".

- записи відсортовані за `upload_time`, найновіші першими;
- на сторінці 10 записів, вибірка йде через `SELECT * FROM images ORDER BY upload_time DESC LIMIT 10 OFFSET <зміщення>`;
- під таблицею кнопки "Попередня сторінка" і "Наступна сторінка"; на першій сторінці вимкнена "Попередня", на останній - "Наступна";
- некоректний номер (`abc`, `0`, від'ємний) відкриває першу сторінку, номер більший за кількість сторінок - останню;
- якщо записів немає, показується повідомлення "Немає завантажених зображень";
- якщо база недоступна, повертається 500 з повідомленням на сторінці.

### POST /delete/`<id>`

Кнопка "Видалити" в кожному рядку надсилає форму на `/delete/<id>?page=N`.

- запис видаляється з бази (`DELETE FROM images WHERE id = %s RETURNING filename`), файл - з папки `/images`, мініатюра - з `/images/thumbs`;
- після успіху відповідь `303` на `/images-list?page=N`, користувач бачить оновлений список на тій самій сторінці;
- якщо запису з таким `id` немає або `id` не число - 404 з повідомленням "Зображення з id N не знайдено";
- якщо запис є, а файлу на диску вже немає, запис однаково видаляється, а в лог пишеться помилка;
- якщо база недоступна - 500.

## Мініатюри

- При кожному завантаженні Pillow робить зменшену копію картинки (`thumbnail`), пропорції зберігаються, більша сторона до 120 px, маленькі картинки не збільшуються. Формат той самий, що й в оригіналу, для gif береться перший кадр.
- Мініатюри лежать у томі `images`, у папці `thumbs/`, з тим самим ім'ям, що й оригінал. Тому Nginx віддає їх за адресою `/images/thumbs/<ім'я_файлу>` без додаткових налаштувань, а в базі нічого додатково зберігати не потрібно.
- У таблиці мініатюра показується квадратом 60x60 (`object-fit: cover`), тому для чітких екранів вона зроблена вдвічі більшою.
- Якщо мініатюру створити не вдалося, завантаження однаково проходить, а причина пишеться в `app.log`.
- У картинок, завантажених до появи мініатюр, файлу в `thumbs/` немає. Для них у таблиці показується сам оригінал, зменшений через CSS (`onerror` у тегу `<img>`).

## Резервне копіювання

Копії бази створюються вбудованим інструментом PostgreSQL `pg_dump` і зберігаються в папці `backups/` у файлах з датою та часом: `backup_2025-01-24_153000.sql`. У git самі копії не потрапляють.

### Скриптом

Контейнери мають бути запущені. З кореня проєкту:

```bash
python backup.py
```

На Linux або в WSL:

```bash
python3 backup.py
```

Скрипт:

1. виконує `pg_dump` у контейнері `postgres_container` і записує дамп у тимчасовий файл усередині контейнера (користувача й базу бере з `.env`);
2. копіює готовий файл через `docker cp` у `backups/backup_<дата>_<час>.sql` і видаляє тимчасовий файл у контейнері;
3. пише в `app.log` рядок `Успіх: резервну копію бази ... створено` або `Помилка: резервну копію бази не створено (<причина>)`;
4. якщо бекап не вдався, недописаний файл не лишається, а скрипт завершується з кодом 1.

Щоб бекап робився за розкладом, скрипт можна додати в cron (Linux/WSL), наприклад щодня о 03:00:

```text
0 3 * * * cd /шлях/до/проєкту && python3 backup.py
```

### Вручну

Те саме, що робить скрипт. Дамп створюється файлом усередині контейнера, а потім копіюється на хост. Команди однаково працюють у bash і в PowerShell. Якщо в `.env` інші користувач або база, їх треба підставити замість `postgres` та `images_db`.

```bash
docker exec postgres_container pg_dump --clean --if-exists -U postgres -f /tmp/backup.sql images_db
```

```bash
docker cp postgres_container:/tmp/backup.sql backups/backup_2025-01-24_153000.sql
```

```bash
docker exec postgres_container rm /tmp/backup.sql
```

Відмінності від команди з ТЗ (`docker exec -t ... pg_dump ... > backup.sql`):

- дамп не передається через вивід `docker exec` і перенаправлення `>` на хості, а пишеться у файл самим `pg_dump` (`-f`) і копіюється через `docker cp` байт у байт. Так файл не залежить ні від псевдотерміналу, ні від оболонки хоста;
- `--clean --if-exists`: дамп спочатку видаляє таблицю `images`, тому відновлення в робочу базу замінює її повністю, а не падає на помилці "already exists".

### Відновлення з резервної копії

1. Переконатися, що контейнери запущені (`docker compose up`).
2. Скопіювати потрібний файл у контейнер бази:

```bash
docker cp backups/backup_2025-01-24_153000.sql postgres_container:/tmp/restore.sql
```

3. Виконати його там же і прибрати тимчасовий файл:

```bash
docker exec postgres_container psql -U postgres -d images_db -f /tmp/restore.sql
```

```bash
docker exec postgres_container rm /tmp/restore.sql
```

4. Відкрити `http://localhost:8080/images-list` і перевірити, що список відповідає копії.

Команда з ТЗ `docker exec -i postgres_container psql -U postgres images_db < backup.sql` теж працює, але тільки в bash: у PowerShell оператор `<` не підтримується. Варіант з `docker cp` і `psql -f` працює в обох.

Таблиця `images` замінюється даними з копії повністю, разом із лічильником `id`, тож нові завантаження продовжують нумерацію. Файли зображень у копію бази не входять, вони лежать у томі `images`.

## Структура проєкту

```text
app.py             Python-бекенд: маршрути, валідація, збереження, робота з базою, логування
backup.py          скрипт резервного копіювання бази
.env.example       приклад налаштувань бази (скопіювати в .env, щоб змінити)
requirements.txt   залежності Python (Pillow, psycopg2-binary)
Dockerfile         образ бекенду (multi-stage build)
compose.yaml       опис сервісів app + nginx + db, томів і мережі
nginx.conf         роздача /images/ та статики, проксування решти на бекенд
db/init.sql        створення таблиці images при першому запуску бази
static/            HTML, CSS, JS інтерфейсу і шаблон сторінки images-list.html
tests/             юніт-тести бекенду
images/            локальна тека для зображень, мініатюри в images/thumbs/ (у Docker - том images)
logs/              локальна тека для логів (у Docker - том logs)
backups/           резервні копії бази
```

## Як влаштована взаємодія

- Nginx слухає `:8080` і є єдиною зовнішньою точкою входу.
- `/images/<файл>` і мініатюри `/images/thumbs/<файл>` Nginx віддає сам із тому `images` - Python при цьому не задіяний.
- Статику (`/css/`, `/js/`, `/img/`) Nginx теж роздає сам із теки `static/`.
- Решту маршрутів Nginx проксує на `http://app:8000`.
- Бекенд звертається до бази за іменем сервісу `db` у внутрішній мережі `app-net`.
- Тіло більше за 6 МБ Nginx відхиляє сам, підміняючи власний 413 на таку саму JSON-помилку 400, як у бекенду.

## Логування

Лог пишеться у `logs/app.log` (том `logs`) у форматі з ТЗ:

```text
[2026-01-24 14:00:00] Успіх: з'єднання з базою даних успішне
[2026-01-24 14:00:05] Успіх: зображення 3f2a1c....png (id 12) завантажено
[2026-01-24 14:01:00] Помилка: непідтримуваний формат файлу (document.txt)
[2026-01-24 14:02:00] Помилка: не вдалося зберегти метадані в базу (cat.png): <причина>
[2026-01-24 14:02:30] Помилка: не вдалося створити мініатюру (cat.png): <причина>
[2026-01-24 14:03:00] Успіх: зображення 3f2a1c....png (id 12) видалено
[2026-01-24 14:04:00] Помилка: зображення з id 99 не знайдено в базі
[2026-01-24 14:05:00] Успіх: резервну копію бази backup_2026-01-24_170500.sql створено (4248 байт)
```

Час у лозі та в базі київський: у `compose.yaml` для бекенду задано `TZ: Europe/Kyiv`, а для бази `timezone=Europe/Kyiv`.

Ті самі записи бекенду дублюються у `docker compose logs app`. Переглянути весь лог:

```bash
docker exec image-server-app cat /logs/app.log
```

## Тестування

```bash
pip install -r requirements.txt
```

```bash
python -m unittest discover -s tests
```

Справжня база для тестів не потрібна: функції роботи з PostgreSQL у тестах підміняються фейковими, а SQL-запити перевіряються на фейковому з'єднанні.

Тести перевіряють:

- завантаження `.jpg`, `.png`, `.gif` і запис правильних метаданих у базу, зокрема для великого файлу;
- відмову для непідтримуваних форматів, файлів більших за 5 МБ і файлів, які лише вдають із себе картинку розширенням;
- що при помилці бази файл не лишається на диску, а причина пишеться в лог;
- нестандартні записи межі `multipart` (у лапках, із додатковим параметром);
- сторінку `/images-list`: колонки, посилання, сортування, екранування назв, повідомлення для порожнього списку;
- пагінацію: 10 і 11 записів, середню сторінку, некоректні та завеликі номери сторінок, `LIMIT` і `OFFSET` у запиті;
- мініатюри: розмір і формат для jpg, png, gif, маленька картинка не збільшується, віддача через `/images/thumbs/`, прибирання при помилці бази, завантаження без мініатюри, колонка прев'ю з запасним варіантом;
- видалення через `/delete/<id>`: запис, файл і мініатюра, редирект, неіснуючий `id`, відсутній файл, картинка без мініатюри, помилку бази;
- перенаправлення старих адрес `/images/` і `/gallery`;
- сторінки інтерфейсу, `HEAD`, коди 404;
- захист від виходу за межі тек зображень і статики.
